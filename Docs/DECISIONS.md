# DECISIONS(決めたことの記録)

## 基盤(項目1)
- ビルド: main・preload は esbuild(CJS、electron だけ外部)、renderer は Vite。`scripts/build.mjs` が `out/` に出す。electron-vite などの追加ツールは使わない(依存を少なく)。
- 追加した依存と理由:
  - `electron` / `typescript` / `vite` / `@vitejs/plugin-react` / `react` / `react-dom` … 技術方針どおり。
  - `esbuild` … main・preload のバンドル(Vite が内部で使うものを明示)。
  - `vitest` / `@playwright/test` … 単体テストと、Electron を起動する自動操作テスト。
  - `zod` … データの型の定義と検証。Claude への出力形式の説明(JSON Schema)も同じ型から作る。
  - `katex` / `marked` … 数式と Markdown の表示。
  - `pdfjs-dist` … PDF のページ画像化(renderer の canvas で描く)。テストでは PDF のページ数・文字の確認にも使う。
  - `@electron/packager` … 配布用のフォルダ形式ビルド。
- テスト時の隔離: 環境変数 `ME_DATA_DIR`(データの場所)、`ME_USER_DATA`(Electron の userData)、`ME_HEADLESS=1`(ウィンドウを出さない)で差し替える。自動テストは必ず `tests/tmp/` か OS の一時フォルダを指す。
- 設定ファイル名は `vite.config.mts` / `vitest.config.mts`(Vite 8 の警告を避けるため ESM 拡張子)。

## Claude Code の呼び出し方(項目2、2026-11-17 に確認)
確認元: `claude --help`(版 2.1.316)と公式ドキュメント(code.claude.com/docs/en/headless、cli-reference、permissions)。

### 使うコマンド(方式A)
```
claude -p --output-format json --permission-mode acceptEdits --tools "Read,Write,Edit,Glob,Grep" --model <モデル> [--resume <session_id>]
```
- 作業フォルダ: 子プロセスの cwd をプロジェクトのフォルダにする(Claude は起動したフォルダを主な作業フォルダとして扱う。専用のオプションは無い。追加は `--add-dir`)。
- プロンプト: 標準入力で渡す(`-p` は標準入力を読む。上限 10MB)。引数に長い日本語を載せない(Windows の引数の制約・エスケープを避ける)。
- `--output-format json`: 標準出力に結果 JSON が1つ出る。実測で使える項目: `result`(最後の返答文)、`is_error`、`subtype`("success" など)、`session_id`、`duration_ms`、`num_turns`、`total_cost_usd`、`permission_denials`。ドキュメントに明記があるのは result / session_id / total_cost_usd。
- `--tools`: 使える組み込みツール自体を絞る。Bash・WebFetch などは一覧から消える(「コマンド実行なし」を満たす)。
- `--permission-mode acceptEdits`: ファイルの書き込みを確認なしで行う。`-p` では、許可の無い操作は確認待ちにならず拒否される。
- `--allowedTools` は「確認なしで実行してよいツール」の指定、`--disallowedTools` は拒否の指定。今回は `--tools` で足りるので使わない。
- `--model`: 別名(`sonnet` / `opus` / `haiku` / `fable`)か正式名。アプリの設定で変えられるようにし、既定は `sonnet`(暫定。速さと費用のため)。空なら `--model` を付けない(Claude Code 側の既定)。
- 続きの会話: 結果 JSON の `session_id` を保存し、次回 `--resume <session_id>` を付ける(質問画面で使う)。`--continue` は「そのフォルダの直近の会話」なので、複数のジョブが並ぶこのアプリでは使わない。
- 終了コード: 成功 0、失敗は 0 以外(ドキュメント)。認証が無いなど実行中の失敗は、失敗内容が標準出力の result として出る。
- プロジェクトフォルダの `.claude/settings.json` には `permissions.allow: ["Read(./**)","Edit(./**)","Write(./**)"]`、`deny: ["Bash","WebFetch","WebSearch"]` を書く(二重の守り)。
- ページ画像(PNG)は Claude の Read ツールで読ませる(Read は画像を読める)。

### 実際に試したコマンドと結果(本物の呼び出し 2 回)
1. `node scripts/try-claude.mjs`(中身は上のコマンド。cwd=tests/tmp/real-check、標準入力で「2+3 の答えを {"answer": 数値} として out.json に書け」)
   - 終了コード 0、5.5 秒。stdout は `{"type":"result","subtype":"success","is_error":false,"result":"完了","session_id":"bc97…","num_turns":2,"permission_denials":[],…}`。`out.json` に `{"answer": 5}` が書かれた。
2. `node scripts/try-claude.mjs --resume bc975881-… "さっき書いた answer の値を数字だけで"`
   - 終了コード 0、2.2 秒。`result: "5"`、同じ `session_id` が返った(会話の続きができる)。

### 失敗の見分け方(暫定)
- claude が無い: 子プロセスの起動が `ENOENT` で失敗する。
- 使用量の上限: 実例(Logs/overnight.log、テキスト出力)は `You've hit your 5-hour limit · resets 12:30am (Asia/Tokyo)`。標準出力・標準エラー・result に `hit your … limit` / `usage limit` / `limit reached` を含むかで判定する。
- 未ログイン: ドキュメントに決まった文言は無い。`Not logged in` / `Please run /login` / `Invalid API key` / `authentication` を含むかで判定する(実物を確認できていないので QUESTIONS.md に記載)。
- 通信失敗: `ECONNRESET` / `ENOTFOUND` / `network` / `fetch failed` / `API Error` / `overloaded` などを含むか。
- どれでもなければ「その他の失敗」として、出力の先頭を画面に出す。

## Claude 呼び出し層とジョブ(項目3)
- 構成: `src/core/claude/runner.ts`(子プロセス1回ぶん)→ `task.ts`(入出力ファイル・型検証・やり直し・記録)→ `src/core/jobs.ts`(ジョブの列)。`src/core/` は Electron に依存させず、Vitest から直接テストする。
- 受け渡しの置き場所: プロジェクト内 `.me/io/<呼び出しID>/input.json`・`output.json`。成功したら消す(内容は logs に残る)。
- プロンプトの約束: 本文(`src/prompts/<種類>.md`)の後ろに共通の `_common.md` を付ける。そこに `ME_PROMPT_KIND:` `ME_INPUT_FILE:` `ME_OUTPUT_FILE:` の3行と、型(zod)から作った JSON Schema を入れる。やり直しのときは `_retry.md`(前回のエラー内容)を足す。
- やり直しは「出力ファイルが無い・JSON として読めない・型に合わない・追加の検査に落ちた」ときだけ(最大2回)。claude 自体の失敗(未ログイン・上限・時間切れ・取り消しなど)はやり直さず、すぐ失敗にする。
- 記録: 呼び出し1回ごとに `logs/<呼び出しID>_<種類>_<何回目>.json`(プロンプト全文・所要時間・終了コード・結果・検証エラー)。
- 1日の上限: データフォルダ直下の `usage.json`(日付と回数)で数える。やり直しも1回と数える。端末の日付が変わると 0 に戻る。
- 1回の呼び出しの制限時間: 既定 15 分(暫定、設定で変更可)。時間切れ・取り消しのときは Windows では `taskkill /T /F` で子プロセスごと止める。
- ジョブはメモリ上だけで持つ(アプリを閉じると一覧は消える。結果はファイルに残っているので困らない)。暫定。
- 偽 Claude: `Tools/fake-claude/fake-claude.mjs`。`ME_FAKE_CLAUDE=1` のとき、アプリは自分自身の実行ファイル(Electron なら `ELECTRON_RUN_AS_NODE=1`)でこのスクリプトを動かす。振る舞いは `ME_FAKE_MODE`(全体)か `ME_FAKE_CONTROL`(JSON ファイル。種類ごと・回数ごと)で切り替える。モード: ok / broken / invalid / nofile / slow / fail / not_logged_in / usage_limit / network、制御ファイルの `notFound: true` で「claude が無い」。受けた呼び出しは `<制御ファイル>.calls.jsonl` に記録され、テストがプロンプトの中身を確かめられる。

## データの型と保存(項目4)
- 型は `src/shared/schema.ts` に zod でまとめる(ファイルの形と、Claude の出力の形の両方)。ファイルの種類の一覧は `src/core/store.ts` の `Files`、置き場所は `src/core/paths.ts`。
- 版番号: すべての JSON ファイルの先頭階層に `version`(いまは全種類 1)。読み込み時に、古い版は `migrations` で1つずつ直し、直した内容で書き戻す(元は `<ファイル>.v<版>.bak`)。アプリより新しい版は読まずにエラー(書き換えない)。版番号が無いものは版 0 とみなす。
- 壊れたファイルは消さずに残し、種類(壊れている/形式違い/新しい版/古すぎる版)を分けて日本語で伝える。
- 保存は「一時ファイル(`<名前>.tmp-<pid>-<乱数>`)に書いて fsync → rename で置き換え」。Windows で rename が一時的に失敗(EPERM/EBUSY)したら少し待って数回やり直す。残った一時ファイルは起動時に掃除する(1分以上前のものだけ)。
- フォルダ名: プロジェクト ID・科目 ID は名前からファイル名に使えない文字を除いたもの(人がフォルダを見て分かるように)。同名があれば `-2` などを付ける。名前を後から変えてもフォルダ名(ID)は変えない。
- CLAUDE.md の構成に足したファイル(細部): 資料ごとの `source.json`(種類・題名・状態)、`extracted.original.json`(Claude が最初に読んだまま。補正率の計算用)、`figures/`(切り出した図)、科目ごとの `review.json`(復習の予定)、テストごとの `explanations.json`・`booklet.pdf`・`answer_sheet.pdf`、プロジェクト直下の `.me/io/`(受け渡しの一時置き場)、データフォルダ直下の `usage.json`。紙の答案 `tests/<ID>/submission/` は資料と同じ構成(original.pdf、pages/、extracted.json、corrections.json)。
- 難易度の設定は2つに分けた: 試験の型(共通テスト/国公立二次/私大)と、目標の高さ(合格最低点をねらう/合格者平均をねらう/上位での合格をねらう)。暫定。

## プロジェクトと画面の窓口(項目5)
- 画面 → main の窓口は IPC `me:call`(機能名+引数)1本だけ。使える機能は `src/core/api.ts` の `createApi()` が返す一覧に限る(一覧に無い名前は断る)。main → 画面の知らせは `me:event`(ジョブの変化)。`createApi` は Electron に依存しないので、単体テストから同じ入口を呼べる。
- プロジェクトの CLAUDE.md のひな形は `src/prompts/project_claude.md`。設定を保存するたびに書き直す。
- プロジェクトの `.claude/settings.json`: allow `Read(./**)` `Edit(./**)` `Write(./**)`、deny `Bash` `PowerShell` `WebFetch` `WebSearch`。
- 科目を外しても科目フォルダは消さない(データを守る)。プロジェクトの削除機能は作っていない(エクスプローラーでフォルダを消す)。暫定。
- 自動操作テストのウィンドウ: 完全に隠す(show:false)と描画が止まり Playwright の操作が1回ごとに数秒かかったため、`ME_HEADLESS=1` のときは画面の外(-20000,-20000)に、フォーカスを取らない形で出す。
- テスト用に、今日の日付は環境変数 `ME_TODAY` で差し替えられる。

## 単元ツリー(項目6)
- 単元は `{id, name, weight, children}`。重みは 0=扱わない、1=ふつう、2=重点、3=最重点。出題の対象は「葉で、自分と親の重みが 0 でない単元」。階層は3段まで。
- 初期ツリーの ID は位置から決める(`u01`、`u01-02`)。Claude の調整では、既存の ID と名前を変えないことをプロンプトで求め、出力の ID の重なり・空の名前は検査してやり直させる。苦手マップなどの記録は単元 ID で結び付ける。
- 初期ツリーは、科目の構成を参考に見出しだけを自作したもの(教科書の文章は使っていない)。

## PDF の取り込み(項目8)
- ページ画像化は画面側(renderer)の canvas で pdf.js を使って行い、PNG を1枚ずつ main に渡して保存する(`importBegin` → `importOriginal` → `importPage`×n → `importFinish`)。途中で失敗したら作りかけの資料フォルダは消す。
- ページ画像の大きさ: 長い辺 1800px(暫定。Claude が読むのに十分で、大きすぎない値)。PDF に文字の層があれば `pages/page-NNN.txt` にも保存し、読み取りの助けにする。
- 画像(JPG/PNG)の取り込み: 複数選ぶとファイル名の順に1枚=1ページ。元ファイルは `original-<n>.<拡張子>`、PDF は `original.pdf`。
- 画面のファイルは `app://renderer/…` という専用の経路で配る(file:// では pdf.js の worker・文字コード表の読み込みに制約があるため)。画面からアプリ外のページへの移動・新しいウィンドウは禁止。
- pdf.js の付属データ(cmaps・standard_fonts・wasm)は、ビルド時に `out/renderer/pdfjs/` へコピーする。
- パスワード付き PDF・壊れた PDF は日本語で断る。
- ページ画像の画面表示は、main からバイト列をもらって blob URL にする(画面にファイルのパスを直接は触らせない)。

## Claude による読み取り(項目9)
- 1回の呼び出しで読むのは 4 ページまで(暫定、`READ_CHUNK_PAGES`)。それより多い資料はページ群に分けて順に読む。2つ目以降の呼び出しには、前のページ群の最後の問題(`previousTail`)を渡し、続きなら `continuesFromPrevious: true` を付けて返させる。
- 結合の決まり: 「続き」の印が付いた先頭の問題は、前の問題に本文(改行でつなぐ)・ページ・図・選択肢・自信のない箇所を足して1問にする。配点などは、前に無ければ後ろの値を使う。先頭のページ群の「続き」印は無視する。
- 問題用と答案用の指示は `src/prompts/read_pages_modes.md` に分けて置き、`read_pages.md` に差し込む。答案用では、テストの設問一覧(`testProblems`)を渡し、どの設問への解答か(`target`)を返させる。
- 推定の単元は、入力に渡した単元の一覧の ID で返させる。一覧に無い ID は空にする(捨てる)。
- 資料に無いページ番号を返したら、理由を添えてやり直させる(型は合うが中身がおかしい場合の検査)。
- 図の切り出しは、ページに対する割合(0〜1)の範囲で受け取り、main 側で Electron の `nativeImage` で切り出して `figures/<問題ID>-f<n>-<乱数>.png` に保存する。core は Electron に依存させないため、切り出しの関数は `AppCore` に外から渡す(単体テストではコピーで代用)。
- Claude が読んだままの結果は `extracted.original.json` に残す(補正率の計算用)。途中のページ群で失敗したら何も保存せず、資料は「未読み取り」のままにする。

## 補正画面(項目10)
- 補正の操作はすべて main 側(`src/core/correction.ts`)で行い、1操作ごとに extracted.json と corrections.json(履歴)を保存する。画面は編集中の1問ぶんだけを手元に持ち、他の操作の前に自動で保存する。
- 内容を変える操作(編集・分割・結合・並べ替え・削除・図・読み直し)をすると、その問題と資料全体の確定が外れる。「資料を確定」は全問題をまとめて確定にする。
- 直した割合(補正率)の目安 = 「Claude が読んだままの本文+選択肢」と「いまの本文+選択肢」の、文字ごとの数の差(増えた数と減った数の大きいほう)÷ 元の文字数。並べ替え・分割・結合だけでは増えない。暫定。
- 自信がない箇所は、数式の中にあることが多くプレビューの中では色を付けにくいので、問題カードの色+一覧+「本文の該当部分を選択」で示す。「確かめた」で印を外せる。
- 1問だけの読み直し(`reread_problem`)は、その問題が載っているページ(最大6枚)だけを渡す。図は、返ってきたときだけ置き換える。
- 問題 ID(`q001`…)は使い回さない(消した・結合した ID も履歴から拾って避ける)。
- 答案の資料(`sub-<テストID>`)を確定すると、設問ごとにまとめた `reading.json`(method: scan, confirmed: true)を書き、テストを「提出済み」にする。確定が外れたら reading.json も未確定に戻す。

## 問題の作成と検算(項目11)
- 流れ: ①作成(`generate_problems`、注文と同じ数・同じ順)→ ②解き直し(`solve_problems`、問題文と選択肢だけを渡す)→ ③照らし合わせ。
- 照らし合わせ: 選択式は番号の一致、短答は見た目の違い(空白・全角半角・`$`)をならして一致すれば手元で合格。書き方が違う短答と記述式は、`judge_answers`(採点基準に照らして満点か)を1回呼んで判定する。解き直しが「条件不足・複数解・矛盾」を報告したら不一致扱い。
- 不一致は、理由と前の問題文を添えて1回だけ作り直す(その問題だけ)。それでも不一致なら破棄し、同じ注文で別の問題を1回だけ作る(図は使わせない)。これも通らなければその注文はあきらめる(問題数が減る)。1つも残らなければテストを作らず失敗にする。暫定。
- 呼び出し回数は、ふつう 2〜3 回(作成・解き直し・照らし合わせ)、最悪 9 回。
- 記録: テストごとの `verify.json` に、採用(adopted)・作り直しで採用(regenerated)・破棄(discarded)の件数と理由。「捨てた問題の代わり」が通った場合は、破棄 1 と採用 1 の両方が残る。
- 図は SVG で描かせる(暫定)。`<svg>…</svg>` の形でない・スクリプトを含む・大きすぎるものは「崩れている」とみなし、図なしで作り直させる。画面では img(data URL)として表示し、スクリプトは動かさない。
- 解き直しの呼び出しはプロジェクトフォルダで動くので、理屈の上では logs/ の中の答えを読める。プロンプトで「ほかのファイルを読まない」と指示している(暫定。厳密にするなら解き直しだけ別フォルダで動かす)。
- 問題の ID はテスト内で `p01`…、番号は `問1`…。問題文(test.json)と答え(answer_key.json)は別ファイル。

## 実力診断テスト(項目12)
- プロンプトの種類 `design_test` を足した。「分量と制限時間は Claude が決める」ため、問題づくりの前に、出題の一覧(単元・難易度・形式)と制限時間・注意書きだけを決めさせる。診断用と模擬試験用の決まりは `design_test_rules.md` に分けて置く。設計の問題数は 30 問まで(暫定)。
- 設計が返した単元 ID が一覧に無ければやり直させる。試験の型と形式の対応(共通テスト=すべて選択式 など)はプロンプトで指示する。
- PDF 出力: core が印刷用の HTML(`src/core/print.ts`)を作り、main が見えないウィンドウで開いて `printToPDF`(A4)する。KaTeX の CSS・フォントは `out/katex/` から読む。保存先はテストのフォルダ(`booklet.pdf`、`answer_sheet.pdf`)。画面には保存先を表示し、「フォルダで表示」できる。
- 問題冊子には答え・解説を入れない。解答用紙は設問ごとの枠(選択式・短答は小さく、記述は大きく)。

## テストを解く・答案を出す(項目13)
- アプリ内で入力した答案は、本人が入力したものなので提出と同時に「確定」扱い(reading.json の method: inapp)。紙の答案は、補正画面で確定するまで採点に使わない(method: scan)。
- 途中の控えはテストのフォルダの `draft.json`(答え・使った時間・延長したか)。入力が 0.4 秒止まったら保存、時間は 10 秒ごと、画面を離れるときにも保存。提出したら消す。
- 制限時間を過ぎたら入力を止めて提出をうながす。「時間を延ばして続ける」も選べる(自動では提出しない。暫定)。かかった時間(elapsedSec)は答案に残し、採点で「時間切れ」の判断材料にする。
- 採点済みのテストは出し直せない。採点前なら、紙 ⇄ アプリ内のどちらでも出し直せる(前の答案は捨てる)。
- 選択肢の記号は ①②③…(画面・PDF 共通)。答えとして保存するのは番号(1始まりの数字)。
- テスト用: 環境変数 `ME_TIMER_SPEED` で解く画面の時計を速められる。

## 採点(項目14)
- 採点は1テストにつき Claude の呼び出し1回(答えのある設問をまとめて渡す)。未解答の設問は呼び出さずに 0 点・「未解答」(かかった時間が制限時間以上なら「時間切れ」)とする。
- 選択式は、Claude の採点に加えて手元でも番号の一致を確かめ、手元の結果を正とする(①②などの記号も番号として読む)。
- 減点があるのにミスの種類が無い・配点を超える点数・採点漏れは、理由を添えてやり直させる。
- 上書きは `grading.json` の各設問の `override`(点数・理由・日時)と、履歴 `overrides`(前の点 → 後の点)に残す。Claude の元の点数は消さない。合計や苦手マップは上書き後の点数で計算する。
- 正解・解き方(answer_key.json)は、採点が済むまで画面に渡さない。
- 採点のあとの処理(苦手マップの更新など)は `onGraded` に登録した関数として呼ぶ(上書きのあとにも呼ぶ)。

## 苦手マップと習熟度の式(項目15、暫定)
- 記録(event)= 1設問の結果: 日付、テスト、設問、得点率(0〜1、上書き後)、難易度、ミスの種類(満点なら無し)。
- 「できる度合い」= 難易度ごとの下限+得点率×(上限−下限)。易: 0〜70、標準: 10〜85、目標校レベル: 25〜100(易しい問題が解けても満点の証拠にはならず、難しい問題を落としても 0 にはしない)。
- 新しさの重み = 0.5^(経過日数 ÷ 30)(30日で半分)。
- 習熟度 = (50×0.5 + Σ できる度合い×重み) ÷ (0.5 + Σ 重み)。記録が無ければ 50(まだ分からない)。記録が少ないうちは 50 に寄り、古い記録しか無い単元も 50 に戻っていく。
- 画面に出す習熟度は、表示のたびに今日の日付で計算し直す(時間がたつと古い結果が軽くなる)。weakness.json の `mastery` と `history`(推移)は、更新した日の値。
- 同じテストを反映し直すとき(上書き)は、そのテストの前の記録を置き換える(二重に数えない。日付は最初のまま)。
- 科目全体の習熟度 = 記録のある単元の習熟度の、単元の重みでの平均。目標の習熟度は、目標の高さごとに 60 / 75 / 85(暫定)。ダッシュボードに「目標まであと◯」を出す。

## 志望校の傾向(項目16)
- 材料は「種類が過去問で、確定した資料」だけ。Claude には設問ごとの番号・大問・配点・形式・推定単元・本文の冒頭 500 字(暫定)を渡す(全文は渡さない。大きさを抑えるため)。
- プロンプトで「入力の過去問に書かれていることだけをもとにする(大学についての記憶で補わない)」「材料が少ないときはその旨を書く」と指示する。
- 更新のきっかけ: 補正画面で過去問を確定したとき(自動でジョブを並べる)と、「傾向」タブの「更新する」。`basedOn`(もとにした資料 ID)と、いまの確定済み過去問がずれていたら「変わっています」と表示する。
- 再診断の提案: 傾向があり、診断テストが1つ以上あり、傾向の更新より後に作った診断テストが無いとき。

## 学習計画(項目17、数値は暫定)
- 週は「計画を作った日」から7日ごとに切り、試験の前日までを計画する。最後の週は短くなることがある。
- 一度に計画するのは 26 週まで。試験がそれより先なら、その旨(`beyond`)を Claude に伝え、近づいたら作り直す(「計画した期間が終わりました」とうながす)。
- 通しの模擬試験: 最後から2つ目の週と4つ目の週に、科目ごとに1回ずつ(週の中で日をずらす)。試験まで1週しか無ければ入れない。試験が計画の範囲より先なら、まだ入れない。作り直しても、すでに作った模擬試験の予定は残す。
- 遅れの判定: 計画を作った日から昨日までの直近7日のうち、採点まで済んだ「今日の課題」が1つも無い日が3日以上 →「作り直し」を提案する(自動では作り直さない)。作り直すと、その日が新しい起点になる。
- 「やらなかった日があっても破綻しない」: 今日の課題は、毎日その日の時点の計画の週・苦手マップ・復習の期限から作る(やらなかった日の分を積み残さない)。Claude には、1週間の時間を使える時間の8割ほどに抑えるよう指示する。
- 試験日が今日 →「今日が試験日です」と案内し、計画は作らない。過去 → 試験日の変更をうながす。
- Claude が返した単元 ID のうち一覧に無いものは捨てる。週の数が合わない・科目 ID が違う出力は、やり直させる。

## 今日の課題(項目18、数値は暫定)
- 今日の課題は「科目ごとに1日1つのテスト」(kind: daily、date: その日)。項目11の問題づくり・検算、項目13〜15の解く・採点・苦手マップをそのまま使う。新しいプロンプトは足していない(注文の「用途」で苦手克服・類題・復習を伝える)。
- 1日にあつかう科目の数 = 1日の時間 ÷ 45 分(1〜3 科目)。計画の今週の時間が多い科目から並べ、日ごとに順番に回す(今週の時間が 0 の科目は出さない)。計画が無くても作れる(科目を順に回す)。
- 1つの課題の問題数 = 科目に割り当てた時間 ÷ 8 分(3〜8 問)。制限時間 = 問題数 × 8 分。
- 中身の順: ①復習(期限が来たもの、古い順、全体の 1/3 まで。形式・難易度はもとの問題に合わせ、もとの問題文を参考として渡す)→ ②過去問の類題(傾向があるときだけ、頻出単元から 1/3 まで、目標校レベル。習熟度 40 未満の単元は標準)→ ③苦手克服問題(習熟度 70 未満の単元。計画の今週の単元を先に。習熟度 40 未満は易、70 未満は標準。よくするミスの種類を添える)。苦手の記録が無いうちは、計画の単元・重みの大きい単元から「演習」として出す。
- 復習の予定は科目ごとの `review.json`。満点でなかった問題を 2 日後に入れ、復習の類題に正解するたびに 2 → 5 → 12 → 30 日と間をあける。30 日後も正解したら終える。間違えたら 2 日後からやり直し。復習の問題そのものは新しい復習を増やさない(もとの問題の予定を動かすだけ)。上書きで満点になったら予定を取り消す。
- 日をまたぐ動作: 「今日の課題」はその日の日付のものだけを出す。やらなかった日の課題は積み残さない(科目の「テストと課題」には残り、あとから解ける)。期限の過ぎた復習は残り、次に作る課題に入る。
- 通しの模擬試験: 計画の予定日が来たら(過ぎて 6 日以内も)ダッシュボードの「今日の課題」に「模擬試験を作る」を出す。作ったテストは計画の予定に結び付ける。
- 偽 Claude の採点の不具合(数字の照合の正規表現が `/d+/` になっていて、短答・記述の正解が満点にならなかった)を直した。

## 解説・授業ノート・質問(項目19、数値は暫定)
- 解説: 採点のジョブが終わると、満点でなかった設問があれば「解説」のジョブを続けて並べる(採点1回につき呼び出しが1回増える。解説が失敗しても採点は済んだまま。結果画面から作り直せる)。設問 8 問ごとに1回の呼び出し。保存先はテストのフォルダの `explanations.json`(画面用)と `explanations.md`(人が読む用。仕様の構成どおり)。PDF は `explanations.pdf`。
- 上書きで間違いが増えたときは、結果画面の「Claude に解説を書かせる」で、解説の無い設問だけを足す。満点になった設問の解説は消さずに、画面で出さない。
- 授業ノート: 単元(葉)ごとに `notes/<単元ID>.md`。Claude には、その単元の苦手の記録・実際に間違えた問題(新しい 6 件、本文の冒頭 400 字と所見)・傾向・前のノート(作り直しのとき)を渡す。自動では作らない(必要に応じてユーザーが単元を選ぶ)。
- 質問: `chats/<ID>.json` に、文脈(テスト+設問 / 授業ノートの単元 / 科目全般)・やりとり・Claude Code の会話 ID を保存する。質問は送った時点で保存し、答えはジョブで付く。失敗したら質問は残り、「もう一度試す」か、質問し直し(答えの付いていない質問は置き換え)ができる。
- 質問のたびに、問題・自分の答案・採点・解説(または授業ノート)・苦手マップの要約(弱い単元 8 件)・これまでのやりとり(新しい 20 件)を入力ファイルで渡す。2往復目からは `--resume <会話ID>` も付ける。続きの呼び出しが「その他の失敗」になったとき(会話の記録が消えた、など)は、`--resume` なしで1回やり直す(やりとりは入力ファイルにあるので続けられる)。
- 採点前の問題についての質問には、正解・解き方を渡さない(プロンプトでも「手がかりまで」と指示)。いまは質問の入口が採点結果の画面なので、ふつうは起きない。

## 品質欄(項目20)
- 数えるだけで Claude は呼ばない。設定画面を開いたときに、全プロジェクトのファイルから集計する。
- 検算: 各テストの verify.json の合計。「1回で通った割合」= 採用 ÷(採用+作り直して採用+破棄)。
- 読み取りの補正率 = 人が直した文字数 ÷ Claude が最初に読み取った文字数(corrections.json の合計)。問題の資料と答案(手書きを含む)は別々に出す。確定・確定取り消しは「操作」の回数に入れない。
- 仕様に無いが、採点の上書きの数(上書きした設問 ÷ 採点した設問)も目安として出す。

## 本物での通し確認と配布ビルド(項目21)
- smoke_real は Electron を起動せず、core のコード(プロジェクト作成 → createTest → submitAnswers → gradeTest)を直接呼ぶ。解説づくり(採点のあとに自動で並ぶジョブ)は通らないので、呼び出しは 3〜5 回に収まる。回数の上限は、アプリの「1日の上限」を 5 にして守る(超えると daily_limit で止まる)。データは `tests/tmp/smoke-real-*/`。

- `@electron/packager` で作る。Electron 本体を取得できないとき(ネットワークなし等)は、`node_modules/electron/dist` を写して `resources/app` にアプリを置く方法に切り替える(実行ファイルのアイコン・版情報は Electron のままになる)。
- アイコンは未設定(Electron の既定)。コード署名なし。

## セッション2 項目1: ログイン切れの見分け
- 実際の文言(ANSWERS.md 1): `Failed to authenticate: OAuth session expired and could not be refreshed`。長い会話では `Prompt is too long · automatic compaction failed: ` が前に付く。
- 判定に足した語: `failed to authenticate` / `oauth session expired` / `could not be refreshed`。使用量上限の判定を先に行う順番は変えていない(上の文言は上限の語を含まない)。

## 体系的な教材: データと目次(セッション2 項目2、数値は暫定)
- 章にする単元 = 単元ツリーの「出題の対象の葉」(重み 0 でないもの)。並びはツリーの順で、上から第1章、第2章…。
- ファイル: `textbook/toc.json`(目次と章の状態)、`chapters/<単元ID>.json`(アプリが読む版。導入・要点・よくある誤り・例題・確認問題・補足を分けて持つ)、`chapters/<単元ID>.md`(同じ内容を人と Claude Code が読める形にしたもの。仕様の構成どおり)、`review/<単元ID>.json`(点検結果の履歴)、`versions/<単元ID>.v<版>.json|md`(前の版)、`pdf/`(PDF 出力)。仕様の構成に `.json` を足した。
- 章の状態は toc.json に持つが、読むたびに実際の状態にそろえる(`syncToc`): 章のファイルが無ければ「未作成」、作るジョブが待ち・実行中なら「作成中」、作り直しの条件に当たれば「作り直しを提案」、それ以外は「完成」。アプリが途中で落ちても「作成中」のまま残らない。
- 厚さ(習熟度 → 詳しさ・例題の数・確認問題の数):
  - 未習の印あり、または習熟度 45 未満 →「詳しい」: 例題 4、確認問題 4、本文 2500〜5000 字。未習は前提の確認から書かせる。
  - 習熟度 45 以上 75 未満、または記録なし(診断前)→「標準」: 例題 2、確認問題 3、1500〜3000 字。
  - 習熟度 75 以上 →「要点中心」: 例題 1(目標校レベル)、確認問題 2、600〜1500 字。
  - 形式: 共通テスト型はすべて選択式。国公立二次は目標校レベルだけ記述、ほかは短答。私大は短答。
- 「作り直しを提案」の条件: (1) 未習の印が、作ったときと変わった。(2) いまの習熟度での厚さの区分が作ったときと違い、かつ習熟度が 15 以上動いた(診断前に作った章は、習熟度が分かって区分が変わったら)。勝手には作り直さない。
- 単元がツリーから外れたとき: 章を作ってあれば「外れた章」として目次の最後に残す(読める・消さない)。作っていなければ目次から消す(未習の印も消える)。
- 既読の印は、作り直しても残す(作り直しはユーザーが選ぶ操作なので。暫定)。

## 体系的な教材: 章の生成と点検(セッション2 項目3、数値は暫定)
- 章づくりの呼び出しの順: ①`chapter_body`(導入・要点・よくある誤り・例題のねらい・図)→ ②`generate_problems`/`solve_problems`/`judge_answers`(例題と確認問題を1回の注文にまとめて作り、検算)→ ③`chapter_review`(本文の点検。例題は検算済みなので参考として渡すだけ)→ ④指摘があれば `chapter_revise`(1回だけ。直したあとの再点検はしない)。
- 本文を先に書かせるのは、例題のねらい(`exampleFocus`)を問題づくりの注文(`focus`)に渡して、本文と例題をそろえるため。問題の由来に「教材の例題」「教材の確認問題」を足した。
- 例題が1つも検算に通らなければ、章は作らず失敗にする。確認問題が1つも通らなくても、例題があれば章は完成にする(確認問題なし)。
- 点検の指摘は「誤り(事実・計算・用語)だけ」に限るようプロンプトで指示(好みの改善提案で毎回修正が走らないように)。修正は、指摘のあった部分の全文を返させ、指摘の無い部分は書き換えさせない。
- 確認問題は章を作るときに「テスト」(kind: practice、`chapterUnitId` に単元 ID、題は「第N章「…」の確認問題」)として保存する。これで、解く・紙で出す・採点・苦手マップ更新が既存の流れのまま使える。制限時間は 1問 8 分。作り直すと新しいテストができ、前のテストは履歴に残る。
- 検算の記録の分け方: 確認問題の分はテストの verify.json、例題の分は `review/<単元ID>.json` の記録の `verify`。品質欄の「問題の検算」は両方の合計。
- 図: 本文の図は `figures`(id・svg・caption)で受け取り、本文の `[[id]]` の行に置く。崩れた SVG・スクリプト入りは捨て、その場所には説明文(caption)を出す。Markdown の版には SVG を入れず、説明文にする。
- 呼び出しの見込み: 1章 5 回(本文 1+作成 1+解き直し 1+照らし合わせ 0〜1+点検 1+修正 0〜1)。最大 12 回(検算の作り直し・差し替えが全部起きたとき。型違いのやり直しは別)。
- まとめて作る: 今日作る章の数 =(1日の上限 − 今日の呼び出し − すでに並んでいる章づくり×5)÷ 5 の切り捨て。残りは toc.json の `deferred`(単元 ID の列)と `deferredAt`(回した日)に残す。回した日より後の日に、目次を開いたとき・アプリの起動時・動作中 10 分ごとに、その日の残りで作れる分だけ続きを並べる。同じ日に続けたいときは、上限を上げてもう一度「まとめて作る」。
- 1日の上限の数え方の日付を `todayString()`(ME_TODAY で差し替え可)にそろえた。
- 作り直しても残すもの: 既読の印、質問から足した補足。作り直しで変わるもの: 版番号、確認問題のテスト。

## 教材への質問(セッション2 項目5、数値は暫定)
- セッション1の「質問」(`chats/<ID>.json`、`postQuestion`/`answerChat`、`--resume`)をそのまま使う。文脈の型 `ChatContext` に `chapterUnitId`(章の質問)と `textbook`(章を指定しない科目全体の質問)を足した。古いファイルは既定値(null / false)で読める。
- 「ここを質問」で選んだ箇所は、その質問のメッセージに `quote` として保存する(1500 字まで)。続きの質問には、それまでの引用も `history` に入れて渡す。
- 章の質問に渡す文脈: 章の本文(導入・要点・よくある誤り・例題・補足)、確認問題は問題文だけ(答えは渡さない)、選んだ箇所、その単元の苦手マップ(`unitWeakness`)、科目の苦手マップの要約、プロジェクトの目標(`project`)。

- 科目全体の質問は、どの章に足すか決まらないので「教材に反映」は出さない。
- 数式の引用: KaTeX の出力に `data-tex`(元の式)と `data-display` を付け、「ここを質問」の引用は数式を `$...$` / `$$...$$` に戻す。数式の途中から選んでも、その数式全体を引用する。

## 縦書きの記法(セッション3 項目3)
Markdown の拡張記法として次の1つに決めた。読み取りは `src/shared/notation.ts` の1か所だけ(`renderMarkdown` が使う。画面・PDF 共通)。数式(`$...$`)・コードの中は対象外。壊れた記法(閉じていない・知らない種類・中身の不足)は元の文字のまま出し、落ちない。`notationErrors` で誤りを見つけられる(Claude の出力の検証に使う)。

| 表すもの | 書き方 | 表示(縦書き) |
|---|---|---|
| ルビ | `{漢字\|かんじ}` | 字の右(`<ruby>`) |
| 傍線(記号つき) | `{{傍線:ア\|本文}}`(記号は省略可 `{{傍線\|本文}}`) | 字の右に線。記号は線の始まりに小さく枠つき、本文の1文字目と改行で離さない |
| 波線 | `{{波線:a\|本文}}` | 右に波線 |
| 二重傍線 | `{{二重傍線:1\|本文}}` | 右に二重線 |
| 傍点 | `{{傍点\|本文}}` | 右にゴマ点(`text-emphasis`) |
| 空欄 | `{{空欄:A}}`、字数つき `{{空欄:B:5}}` | 枠。既定 3 字分、`:5` で 5 字分(1〜40) |
| 段落番号 | `{{段落:1}}`(段落の頭) | 丸囲みの小さな番号 |
| 語注(本文側) | `{{注:1\|語}}` | 語のあとに小さく「*1」 |
| 語注(注の文) | `{{注記:1\|説明}}` | 「*1 説明」(本文のあとに置く) |
| 縦中横(明示) | `{{縦中横\|!?}}` | 2桁までの半角数字・「!?」「!!」は自動 |
| 再読文字 | `{{再読:未\|いまダ\|ず}}` | 右に1回目の読み(ルビ)、左下に2回目の読み |
| 漢文の区切り | `:::漢文 白文` / `:::漢文 訓読文` / `:::漢文 書き下し文` … `:::`(それぞれ行の頭) | 白文・訓読文・書き下し文を区別(`data-kind`) |
| 送り仮名 | (訓読文の中だけ)`字[_ビテ]` | 字の右下に小さく |
| 返り点 | (訓読文の中だけ)`字[^レ]`、`[^一]`、`[^二]`、`[^上]`、`[^一レ]` など | 字の左下に小さく |

- 入れ子: 傍線・傍点の中にルビを入れられる(`{{傍線:イ|{夕暮|ゆうぐ}れの空}}`)。
- 横書きの科目で同じ記法が出ても、ルビは上、傍線は下線、返り点・送り仮名は字のあとに小さく上下2段で出る(壊れない)。
- 訓読文の外の `[_…]` `[^…]` は記法として扱わない(配列の添字などを壊さない)。
- 記号・空欄・段落番号の書体はゴシック、本文は明朝。
- 記法の一覧と自作の見本(現代文・古文・漢文)は、科目の設定の「縦書きの記法の一覧と見本」で見られる(`src/shared/notation_samples.ts`)。

## 縦書きの PDF(セッション3 項目6、数値は暫定)
- 国語の科目では、問題冊子・解答用紙・教材の PDF を、ページ全体を `writing-mode: vertical-rl` にして Electron の印刷機能で出す。行は右から左、1ページ目は右端の行から、続きは次のページの右端へ(Chromium の縦書きのページ分け)。用紙は A4 縦。
- 問題冊子: 問題の途中でもページをまたいでよい(縦書きでは「問題ごとに改ページしない」を外した。長い本文で大きな空白が出るのを避けるため)。行の途中では切れない。
- 解答用紙(縦書き): 設問ごとに縦長の欄(右端に設問の番号)。選択式は丸い番号のマーク欄。設問の文に「四十字以内」「80字程度」など字数の指定があれば、その字数ぶんのマス目(1行 20 マス、7.5mm 角)。指定が無い短答・記述は罫線の欄(短答 60×20mm、記述 120×60mm)。字数は算用数字・漢数字(十・百を含む)から読む(`charLimit`)。
- 解説の PDF は横書きのまま(CLAUDE.md の「解説は横書き」)。
- 教材の PDF(国語)は、例題の解答・解説も含めて縦書きにそろえた(紙で通して読むものなので。画面では解説は横書き)。
- smoke_real に `--kokugo`(現代文1問・漢文1問の選択式を作る → 検算。呼び出し4回まで)。画面での確認は `tests/e2e/99-view-smoke.spec.ts`(作業フォルダを `ME_SMOKE_DIR` か `tests/tmp/smoke-view-dir.txt` で渡したときだけ動く)。
- 本物の確認を受けて: 訓読文の外の `[_…]` `[^…]` は記法の誤りにしない(解説で「登[^レ]山」と引用することがあり、やり直しが1回むだに起きた)。返り点の付け忘れを防ぐ指示(作る側)と、解き直しで返り点と書き下しが合わなければ「問題の不備」とする指示(検算側)を足した。
